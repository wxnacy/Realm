# AI 聊天附件（产品说明）

> **维护约定（重要）**：本文档是 AI 聊天框附件功能（拖拽/粘贴文件与图片、附件卡片、
> 图片内联渲染）的**产品说明权威文档**。以后修改附件的交互方式、快照语义、注入格式、
> vision 通道、持久化与历史恢复等行为，**必须同步更新本文档**。沙箱与工具侧的说明见
> [ai-agent-workspace.md](ai-agent-workspace.md)（其「聊天附件（attachments/）」小节
> 与本文档互为引用）。

## 一、功能概述

用户可以把本地文件、文件夹、图片**拖拽到 AI 面板整个区域**，或在输入框**粘贴**文件/截图，
作为附件随消息发送给 AI Agent。图片直接渲染在聊天气泡中（可放大、右键下载）；
文件以附件徽标展示。Agent 收到附件快照的路径 marker，可直接读取内容。

对标参考：openhanako（HanaAgent）的聊天附件交互。

## 二、用户交互

### 拖拽（整个 AI 面板都是投放区）

- **投放区域 = 整个 AI 助手面板**（消息列表、头部、输入框任意位置松手都算），不只限于小输入框
- 拖拽悬停时显示覆盖整个面板的虚线遮罩「松开以添加附件」
- 拖拽窗口外松手 / Escape / 窗口失焦时自动结束拖拽态
- 文件误拖到网页（webview）上不会触发导航（document 级兜底拦截）
- **不接管**的拖拽：面板收起时、收藏栏书签拖拽（自定义 MIME）、纯文本拖选

### 粘贴（输入框）

三级优先：

1. **剪贴板里有文件**（Finder 复制文件等）→ 登记为附件
2. **剪贴板里是图片数据**（截图工具按 Cmd+Shift+Ctrl+4 等）→ 登记为图片附件
3. **纯文本** → 放行默认粘贴行为，完全不受影响

### 附件卡片

- 待发送附件显示在输入框上方的胶囊（pill）列表：**类型图标**（图片附件优先显示缩略图）
  + 文件名 + 大小 + 移除按钮
- 上限 **9 个**，超出部分丢弃并提示
- 单文件 > 100MB 时软提示（复制耗时预期），不做硬限制
- 同一文件重复添加只保留一份（内容级去重）

## 三、快照语义（核心机制）

附件登记时，主进程把源文件**复制快照**到 agent 工作区的 `attachments/` 目录
（`userData/agent-workspace/attachments/`，唯一文件名 = 净化原名 + 时间戳 + 随机后缀）：

- **原文件不受任何影响**；后续修改原文件不影响已发送的附件
- **目录附件递归复制**（agent 只能读工作区内，不复制则目录无意义）
- 快照在工作区沙箱内，Agent 用 `read` 工具**零改动可读**
- **不做自动清理**——历史会话回看依赖快照持久存在；磁盘随使用积累（已知技术债）

去重：同一源文件（realpath + 大小 + 修改时间）或同一图片内容（sha256）重复登记时
返回既有附件，不重复复制。

## 四、授权与安全边界

- **授权语义：用户拖入/粘贴即显式授权**（与「文件选择器导入」同一信任级别），
  不弹确认卡片——确认卡片只用于 AI 发起的动作
- **敏感路径启发式屏蔽**（拒绝登记）：`~/.ssh`、`~/.gnupg`、`~/.aws`、`~/.kube`、
  `~/Library/Keychains`、`.env`、`.bash_history`/`.zsh_history`
- **symlink 源拒绝**（防绕道读取链接目标）
- **诚实声明**：敏感路径屏蔽是启发式（防手滑拖整目录连坐敏感文件），
  **不是安全边界**——用户显式拖单个敏感文件仍可绕过，与 bash 白名单同一哲学
- 发送时 renderer 只持登记 ID，主进程从登记表反查快照路径，renderer 无法伪造路径
  指向 attachments 目录之外；历史恢复的按路径读取同样强制校验落点在 attachments 目录内

## 五、发送与注入

发送时附件转成文本 **marker 置于用户正文最前**（先于 @ 引用标签页的 XML 块）：

```
[attached_image: <快照路径>] 截图.png（图片，已同步附于消息）
[attached_file: <快照路径>] 报告.pdf
[attached_file: <快照路径>/] 素材/（目录，可递归读取）

（用户正文，可为空——纯附件发送）
```

图片行的括号措辞按通道条件化（详见 5.1/5.2）：

- 原生直发（主模型判定支持图片）：`（图片，已同步附于消息）`
- 原生直发（判定不支持但未配置视觉模型，回退直发）：`（图片，已随消息附上；若你无法查看图片内容，请如实告知用户你看不到图片，不要猜测或编造图片内容）`
- 视觉桥：`（图片，已由视觉模型转写为文字描述，见下方 <image-descriptions> 块）`

**措辞纪律：绝不能让 marker 声称模型能看到实际不存在的东西**——2026-09-05
幻觉事故的根源正是 marker 谎称「已同步附于消息」而图片未直发。

图片附件按**主模型能力分两通道**（决策内聚主进程 `promptWithContext`）：

### 5.1 原生直发（默认）

以原生图片块（base64）随消息发出（`agent.prompt(text, images)`）。覆盖两种
情况：

- **主模型判定支持图片**（pi-ai `Model.input` 含 `image`，自定义供应商模型
  按 ID `/-vl-|vision/i` 正则兜底）：marker 措辞「已同步附于消息」
- **主模型判定不支持图片但未配置视觉模型**（回退直发）：保留直发是因为
  目录元数据可能误判——实测 mimo 系列支持视觉但目录 `input:['text']`。
  模型真支持则直接看到图；真不支持时 SDK `downgradeUnsupportedImages`
  自动把图片块降级为「图片被省略」占位符，模型收到明确信号，能如实回答
  看不到图。marker 用中性措辞「已随消息附上；若你无法查看图片内容，请如实
  告知用户你看不到图片，不要猜测或编造图片内容」

  > 事故参考（2026-09-05 image.png 幻觉）：初版实现在此情况不传图，但
  > marker 仍谎称「已同步附于消息」，模型相信了这句话又看不到图，编造出
  > 图片内容（mimo 把代码截图说成自己的「证件照」）。教训：**绝不能让
  > marker 声称模型能看到实际不存在的东西**。

  **不做词典门控**——模型能力词典（models.dev 快照）经实测不可靠（存在
  支持视觉但词典无视觉位的模型）；万一供应商拒绝，错误信息对用户可见

### 5.2 视觉桥（Vision Bridge，主模型不支持图片且已配置视觉模型）

主模型 `Model.input` 不含 `image`（自定义供应商模型按 ID `/-vl-|vision/i`
正则兜底）且设置页已配置视觉模型时：

- **图片不再直发**，逐张读快照发给视觉专用模型（pi-ai `completeSimple`
  非流式单轮调用，单图 60s 超时），转写为中文文字描述
- 描述以 `<image-descriptions>` XML 块并入用户正文（多图按
  `[图片 N/M: 文件名]` 分节），marker 措辞同步改为「已由视觉模型转写为
  文字描述，见下方 <image-descriptions> 块」（避免模型误以为能看到图）
- 描述提示词为 5 段式：【画面概述】【可见文字】（原样转录含代码/报错）、
  【内容与布局】【图表与数据】【与用户请求的关联】；单图上限约 3000 字符
- 转写带上用户消息原文（截断 500 字符）作为上下文，让描述聚焦用户意图
- **缓存**：同图 + 同用户请求 + 同视觉模型命中内存缓存（上限 50 条 FIFO），
  同图追问不重复调用
- **失败降级（永不 throw）**：单图失败（超时/限流/空响应等）该图丢弃计入
  失败数，成功部分照常注入；有失败时消息前置通告，要求主模型明确告知用户
  「没有看到图片」；全部失败时仅通告无描述块

- 纯附件发送（正文为空）合法；对话标题回落为附件文件名拼接

## 六、视觉专用模型配置

- **全局唯一**一个视觉模型，存储键 `ai.visionModel = { provider, model }`
  （electron-store `realm-config.json`），引用任意已配置供应商的模型并复用其
  API Key；`{ provider: null }` 即清除
- 设置页 AI 分区「视觉模型（图片转文字描述）」卡片：下拉只列出已配置且未禁用
  供应商下**支持图片输入**的模型（`imageCapable` 由主进程按 `Model.input` +
  ID 正则计算），**即改即存**（change 直接 POST）
- 配置写入前服务端校验：供应商须已配置（Key 可解析，含环境变量回退）、未禁用、
  模型在该供应商可用列表内且具备图片能力
- **有效性警示**：配置存在但当前不可解析（供应商被禁用/Key 失效/模型被删）时，
  下拉旁显示黄色警示；运行时走「未配置」分支（纯 marker）
- **删除联动**：删除供应商时若视觉模型引用指向该供应商，自动清除该配置
- 主进程运行时二次复核：视觉模型对象必须真支持图片输入，否则视同未配置
  （防止 SDK 对 text-only 模型把图片静默降级为占位符造成「描述成功」的假象）

## 七、图片内联渲染

聊天气泡中的图片附件**直接渲染为图片**（与 AI 截图工具的渲染同款交互）：

- 左键点击放大/缩小（居中 + 遮罩，最大 90vw/90vh）
- 右键「下载图片」（保留原始文件名与格式）
- 气泡内图片最大宽 420px（不超过气泡宽度）
- 图片数据经专用通道读取：优先按登记 ID；**历史会话恢复**（应用重启后登记表已空）
  按快照路径读取，路径强制校验在 attachments 目录内
- 渲染失败回退（>25MB / 快照被清理 / 路径失效）：显示类型图标 + 文件名徽标

非图片附件在气泡中显示为「图标 + 文件名」徽标行；图片附件不重复显示徽标。

## 八、持久化与历史恢复

- 附件元数据（名称/快照路径/类型/大小，**不含图片数据**）随用户消息持久化到
  会话数据库（messages 表 attachments 列，旧库自动迁移）
- 重开对话/重启应用后：附件徽标与图片正常回显（按快照路径读取）
- Agent 侧历史靠 marker 文本（含路径）保底——快照文件持久在沙箱内，
  后续轮次仍可 re-read；快照被外部清理后按「渲染回退」呈现，Agent 读取会得到
  文件不存在的结果
- 登记表（attachmentId → 元数据）为应用生命周期内存结构，不跨重启——
  这不影响历史恢复（走路径通道）

## 九、边界与已知限制

| 项 | 行为 |
|----|------|
| 附件数量上限 | 9 个，超出丢弃并提示 |
| 大小限制 | 无硬限制；>100MB 软提示；视觉转写单图上限 25MB（超限跳过并计入失败通告） |
| 快照清理 | 无自动 GC，磁盘持续积累（技术债） |
| 附件点击 | 气泡内徽标仅展示，不打开原文件（后续增强） |
| 压缩 | 不做图片压缩/转码（对标 openhanako 桌面端） |
| vision 失败 | 原生通道供应商拒绝时整轮报错可见；视觉桥单图失败降级为通告不阻断；marker + read 工具是天然兜底 |
