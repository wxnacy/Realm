<objective>
修复 UAT Test 5 / Test 7 两个同根因缺口：收藏夹页面（realm://favorites）空白区域右键显示的是网页通用菜单，而非自定义新建菜单（新建文件夹/粘贴/按名称排序），导致剪切后无法在目标文件夹空白处粘贴。

根因（已由 .planning/debug/favorites-blank-area-context-menu.md 确认，不再重新排查）：空白区域 contextmenu 监听绑在 #favoritesContent（favorites-page.js:1347），该元素无 CSS 规则、作为 flex 子项高度坍缩为内容高度，可见空白实际属于父容器 .favorites-content-area，事件冒泡路径不经过监听元素，处理器永不触发；左侧 #folderTree 从未绑定空白监听。两条空白路径都无人 preventDefault，Chromium 遂透传给 embedder：webview context-menu（renderer.js:833，不过滤内部页面）→ IPC → 主进程弹 Phase-13 通用网页菜单。

Purpose: 让 FOLDER-08 验收标准中的「空白区域右键菜单」在所有几何空白路径上可达（D-08 新建文件夹右键入口、D-10 空白区域菜单项、D-11 内部剪贴板粘贴）。

Output: 事件覆盖无缺口的收藏夹页面 —— 任何空白右键路径都有处理器调用 e.preventDefault() 并弹出自定义菜单；不改动 renderer.js / main.js 的右键透传管线。

修复方案（诊断推荐方向 A）：把空白监听从 #favoritesContent 提升到 .favorites-main 级做委托路由。收藏项/文件夹节点处理器已有 preventDefault + stopPropagation（favorites-page.js:704-705、783-784），事件不会冒泡到 .favorites-main，天然不冲突。不采用 renderer.js 侧过滤内部页面的方案 —— 搜索框等交互元素依赖 webview 透传管线获得默认编辑菜单，过滤会把它们一并误杀。
</objective>

目标：让两个面板的所有空白区域右键都路由到 showEmptyContextMenu 并 preventDefault。只改 setupEventListeners 末尾（约 1333-1349 行）和 showEmptyContextMenu 的守卫（约 858-862 行），其余逻辑不动。

## 1.1 删除失效的旧绑定

删除 setupEventListeners 末尾（当前约 1346-1349 行）对 id 为 favoritesContent 的元素注册 contextmenu 监听、回调内调用 showEmptyContextMenu 的整个代码块。该绑定几何上覆盖不到可见空白（元素无 CSS 规则、flex 高度坍缩），是本次缺口的直接根因。删除后整份文件中不得再残留该元素的事件注册调用表达式——验收会做负向 grep，因此也不要在注释里以「原绑定已移除」之类形式复述该调用表达式，删除即删除，不留墓碑注释。

## 1.2 在同一位置（滚动加载绑定之后）新增 .favorites-main 委托路由

参照紧邻上方 contentArea 的既有写法（约 1334 行，document.querySelector 取元素后判空再绑定），新增：

- 用 document.querySelector 取 '.favorites-main' 元素（favorites.html:30，左右两栏的公共父容器），判空后注册 contextmenu 监听。
- 处理器内按顺序执行三道守卫/动作：
  1. 守卫一：若 e.target.closest 命中 '.favorite-item, .folder-tree-item'（任一即可，逗号选择器）则直接 return。收藏项/文件夹节点有各自处理器且已 stopPropagation，正常不会到达这里，此为防御性守卫。
  2. 守卫二：若 e.target.closest 命中交互元素集合 'input, textarea, select, button, a, dialog, .context-menu, [contenteditable]' 则直接 return。理由：搜索输入框右键需要默认编辑菜单（走 webview 透传管线）；按钮/链接/弹窗/已打开的自定义菜单上不应弹新建菜单。
  3. 调用 e.stopPropagation()，然后调用 showEmptyContextMenu(e)。stopPropagation 必须保留并在 showEmptyContextMenu 之前执行：showContextMenu 每次打开菜单都会在 document 上注册 contextmenu 隐藏监听（favorites-page.js:682-685），若事件继续冒泡到 document，旧的隐藏监听会在同一事件分发中把刚打开的新菜单立即关掉（菜单闪关）。
- 为该处理器上方加一段块注释，说明委托路由的存在理由：可见空白几何上分属 .favorites-content-area 与 #folderTree 两个不同容器，只有公共祖先 .favorites-main 能单点覆盖；并说明 stopPropagation 是为了避开 document 级隐藏监听。遵循项目 JSDoc/注释规范（2 空格缩进、单引号、分号）。

## 1.3 扩展 showEmptyContextMenu 的守卫

showEmptyContextMenu（约 858-862 行）当前第一道守卫只排除 '.favorite-item'。把该 closest 选择器扩展为 '.favorite-item, .folder-tree-item'，与 1.2 的守卫一保持一致（诊断要求补 .folder-tree-item 以区分左右面板）。e.preventDefault() 保持不动——它是关键不变量：guest 页面 preventDefault 后 Chromium 不再向 embedder 透传 context-menu，主进程通用网页菜单就不会弹出。

## 明确不要做的事

- 不要改 renderer.js:833 的 webview context-menu 转发逻辑，也不要给主进程菜单管线加内部页面过滤——搜索框默认编辑菜单依赖这条管线。
- 不要改 showFavoriteContextMenu / showFolderContextMenu / showContextMenu / hideContextMenu 的任何逻辑。
- 不要引入新 IPC 或恢复 Electron 原生 Menu API（维持 15-01 执行期对 D-09 的覆盖决策：HTML 自定义菜单，因为 webview guest 无法走 IPC）。
